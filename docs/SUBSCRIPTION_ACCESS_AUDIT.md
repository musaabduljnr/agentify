# Subscription Access and Quota Audit

## Scope and method

This audit follows the subscription-sensitive paths found in the application source, server actions, API routes, plan configuration, usage helpers, and checked-in Supabase SQL. It is a source review only: the production Supabase schema, migration ledger, provider dashboard, and live webhook state are not available here. Findings below describe checked-in code, not the deployed database.

This document records the pre-implementation findings. For the changes made in response, validation, and deployment limitations, see [SUBSCRIPTION_ACCESS_IMPLEMENTATION_REPORT.md](./SUBSCRIPTION_ACCESS_IMPLEMENTATION_REPORT.md).

The entitlement policy to implement is: a business receives plan features and quota only when its subscription is recognized, verified, and active. A selected plan, a pending checkout, a missing subscription, an unknown plan, or an inactive subscription must not grant plan features. Historical data should remain readable where possible, but mutations and paid processing must be gated on the server. Demo access is a separate, bounded product flow and must not imply a paid subscription.

## Current plan and subscription model

| Area | Current behavior | Risk / required policy |
|---|---|---|
| Plan catalog | `lib/billing/plans.ts` defines Starter, Growth, Enterprise, and a grandfathered Business plan. | Keep these existing product decisions; do not make a new free plan or change published limits without authorization. |
| Unknown plan resolution | `getPlanConfig()` falls back to Starter, and `getEffectivePlanConfig()` also falls back to effective Starter. | An invalid or legacy-unknown plan can inherit Starter access. Authorization must reject unknown plan IDs instead of using display/configuration fallback behavior. |
| Onboarding | `lib/actions/onboarding.ts` creates a Starter subscription with `status: "pending"` and copies Starter limits. | Pending is correctly not active, but downstream quota checks may still treat copied limits as permission. Keep account setup/checkout available while denying paid operations. |
| Setup repair | `lib/actions/repair-setup.ts` can create the same pending Starter record. | Same pending-state risk. Do not repair by granting active status or features. |
| Demo claim | `claimDemoAssistant()` in `lib/actions/demo-generator.ts` transfers a demo business and creates/resets a pending Starter subscription. | Preserve conversion behavior, but the claimed business stays gated until verified payment. |
| Provider activation | Bachs payment processing and subscription helpers are separate from feature checks. | Access resolution must consume only trusted server-side subscription state; provider checkout initiation or a client-selected plan is not proof of payment. |
| Dashboard plan display | `app/dashboard/layout.tsx` and `app/dashboard/settings/team/page.tsx` use Starter fallbacks when plan data is missing. | Display fallback must not become authorization or quota input. |

## Cross-cutting database and quota observations

- The checked-in legacy SQL policies for `knowledge_sources`, `assistants`, `widget_configs`, and `subscriptions` primarily scope rows by business ownership. They do not encode plan entitlements or quota limits. RLS is not a substitute for server-side entitlement checks.
- Several service-role paths bypass RLS by design. Every such path must perform its own authenticated business/ownership validation and subscription check.
- `checkUsageLimit()` and subsequent `incrementUsage()` are separate operations. Concurrent requests can all pass the check, then exceed message, embedding, knowledge, or lead limits. The message counter RPC alone does not reserve capacity atomically with the limit check.
- Some Supabase query errors in usage verification are ignored, which can produce zero-use/success-shaped outcomes. Authorization and quota reservation must fail closed on database errors.
- Existing subscription and usage tables are used by migrations and runtime code, but this repository cannot establish which migrations have actually run in production. Any schema change must be additive, preserve historical rows, and be reported as unapplied until verified.

## Required implementation direction

1. Add one server-only entitlement resolver that binds the authenticated caller to the requested business, loads the authoritative subscription, validates a known plan, and returns no features unless subscription status is verified active. Pending, missing, inactive, unknown, and database-error states deny paid access.
2. Keep plan display/configuration fallbacks separate from authorization. No default Starter entitlement may be inferred for a missing subscription.
3. Apply checks at every server action and API route that creates/changes paid resources, starts AI/provider work, or serves a subscription-dependent public feature. UI gates are supplementary only.
4. Replace check-then-increment quota logic with atomic server-side reservations covering both monthly and applicable daily limits, and make downstream failures release or account for reservations consistently.
5. Preserve appropriate historical reads and billing/checkout/setup actions for inactive users; do not delete data or silently change existing plan limits. Define and test downgrade behavior for existing resources above a new limit.
6. Add tests for missing/pending/active/inactive/unknown subscriptions, Starter and Growth limits, direct action/API invocation, ownership, database failures, over-limit downgrade states, and concurrent reservation attempts.

## Known gaps and verification limits

This report is based on the checked-out source and legacy SQL. It does not assert production database state, RLS policy deployment, migration application, or live payment-provider behavior. Those must be verified separately before claiming production enforcement.
